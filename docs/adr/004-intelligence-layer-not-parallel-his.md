# ADR-004: Intelligence Layer on Existing HIS, Not a Parallel System

## Status
Accepted

## Context
The technical prompt names three engines (MAMA-AI, ULALO-AI, CHUMA-AI) and a full CHW data model. Principle 4 is explicit: **do not build parallel data collection**. Malawi already runs DHIS2, iCHIS/CHT, and LMIS. A fourth registry would split the CHW's day, duplicate households, and fail MoH adoption.

The current monorepo looks like five products (Android app, three dashboards, ML, API). That shape is useful for a demo. It is the wrong shape for a 20-CHW Nsanje pilot.

## Decision
Treat Zisamale as **advisory software that sits on iCHIS/DHIS2/LMIS**:

1. One CHW app, not three. MAMA / ULALO / CHUMA are engines inside that app and the API, not separate installs.
2. One FastAPI process until a real scale bottleneck appears. Do not split cloud services to match the diagram.
3. Visit forms must converge on iCHIS/CHT fields. Until a CHT adapter exists, keep our schema *mappable* (same concepts, client UUIDs, override flags) and do not add parallel household demographics that iCHIS already stores.
4. Cloud ML trains on **outcomes and CHW overrides**, never on labels generated by the same rule that scores the visit.
5. Dashboards exist to close loops (acknowledge alert, assign stock, review overrides), not to display synthetic Nsanje charts.

## Consequences
- **Positive:** Pilot scope matches VillageReach's actual insertion point; MoH is not asked to abandon iCHIS.
- **Positive:** Engineering time goes to sync, tenancy, HITL, and DHIS2 pull — the things that fail in rural Malawi.
- **Negative:** The architecture diagram overstates microservices, Kong, Timescale, LSTM, and NLG. Those stay out of the critical path.
- **Mitigation:** Phase 1–2 of the prompt (foundation + MAMA-AI MVP for 20 CHWs) is the only committed roadmap. ULALO/CHUMA dashboards stay read-models on the same API.
